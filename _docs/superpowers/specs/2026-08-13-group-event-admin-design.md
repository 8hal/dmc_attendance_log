날짜: 2026-08-13

## 1. 배경

철원 마라톤을 **베타**로 운영하고, 하반기 단체 대회를 돌리며 디벨롭한다.

회원 앱(버스 → 배번 → 명단·결과)과 달리, 총무는 지금 `boarding-admin` · `ops.html` · `group-detail` 등 **여러 페이지**로 나뉘어 비효율적이다. 철원 베타부터 **운영은 한 페이지**에서 한다.

동시에 결과 모델이 바뀐다. 참가자가 **배번을 넣으면** 그 번호로 기록을 가져오고, **배번이 없으면 참가하지 않은 것**으로 본다. 이름 매칭 **갭 UI는 주경로에서 제거**한다. 스크랩만으로는 `race_results`에 안 올라가고, **참가자가 본인 기록을 컨펌**해야 대회기록에 반영된다.

---

## 2. 목표 · 비목표

### 2.1 목표

- 총무용 **한 페이지** `event-admin.html?eventId=` (가칭)
- 관리자 비밀번호 1회 (`verify-admin`)
- 섹션: 준비 → 버스 탑승 → 배번 현황 → 결과 스크랩
- 탑승 **수동 on/off** (시간 자동 개폐 없음)
- 대리 탑승 체크, CSV·QR, 배번 있는 사람만 스크랩
- 회원 앱에서 **참가자 컨펌** → `race_results` 반영

### 2.2 비목표 (철원 베타)

- 탑승 시간 자동 개폐
- 중식·좌석·결제·알림톡
- 이름 기반 갭 UI / 총무 일괄 `bulk-confirm`을 운영 홈 주경로로 이식
- 회원·운영 단일 셸
- 결과 보드·외부 기록 딥링크 고도화
- `group-events` BE 전면 재작성
- 네이버 폼 API 자동 연동 (CSV 수동만)
- DNS/DNF·오배번 전용 UI 고도화 (예외는 최소 안내만)

## 3. 역할 분담

| 역할 | 화면 | 하는 일 |
|------|------|---------|
| **총무** | `event-admin` | 탑승 on/off · CSV·QR · 대리 탑승 · 배번 현황 · **스크랩 실행** |
| **참가자** | 회원 앱 (홈 / 명단·결과) | 배번 입력 · **내 기록 확인·컨펌** |
| 배번 없음 | — | 스크랩·컨펌 대상 아님 (= 미참가) |

```
총무 스크랩 → 배번별 조회 결과 대기
     → 참가자 컨펌 → race_results (대회기록 SSOT)
```

---

## 4. 페이지 구조 (`event-admin`)

```
비밀번호
  → 헤더 (대회명)
  → 사이드/상단 메뉴 (준비 | 버스 | 배번 | 스크랩) + 회원 앱 링크
  → 한 번에 한 패널
```

모바일은 메뉴가 상단 가로 스크롤. 기본 패널은 지금 단계 추정 (`EventAdminPanels`), `#prep` 등 해시 우선. 구 링크(`boarding-admin`, `group.html`)는 주경로에 두지 않음.

### 4.1 ① 준비

- 탑승 **on/off** 토글 (수동)
- 버스 명단 CSV import
- 회원 앱 / 버스 참가자 링크·QR 복사
- (필요 시) `groupSource` 설정 — 기존 `group-events` `source` 재사용

**규칙:** `enabled !== true`이면 참가자 셀프체크·대리체크·import 불가. 조회·재활성화만 가능. (버스 Phase 1 스펙과 동일)

### 4.2 ② 버스 탑승

- 가는/오는 탭
- 탑승 n / 미탑승 m, 미탑승 강조
- 행마다 대리 체크·취소
- 지인 추가·제외, 비고(총무만)

**API:** `bus-boarding` — `status`(admin), `admin-board`, `roster-upsert` / `roster-remove`, `import`, `settings`  
**규칙:** `busBoarding.roster` ≠ `participants`. 지인은 탑승만, 배번/결과 기본 제외.

### 4.3 ③ 배번 현황

- `배번 있음 N` / `없음 M`
- 미입력 닉 목록 (독려·연락용)

**API:** `group-events` `detail`의 `participants[]` (`bib`, nickname, distance, …)  
**규칙:** 이름 갭·후보 선택 UI **없음**.

### 4.4 ④ 결과 가져오기

- 소스 표시
- 「배번 N명 스크랩」버튼 · 진행/완료/실패 · 재실행
- 스크랩 후 **대기 건수 / 참가자 컨펌 완료 건수** 요약 (총무가 독려용으로 봄)
- 총무가 대신 컨펌하는 UI는 **주경로에 두지 않음**

**API:** `group-events` `scrape`를 **배번 있는 participant만** 조회하도록 최소 확장.  
스크랩 결과는 기존처럼 job/대기 상태에 두고, **`race_results` 쓰기는 참가자 컨펌 API**가 담당.

## 5. 참가자 컨펌 (회원 앱)

### 5.1 UX

- 위치: **홈 배너** 및/또는 **명단·결과의 ‘나’ 행** (철원 베타에서 하나 이상 제공)
- 배번이 있고 스크랩으로 본인 기록이 준비되면 「내 기록 확인 · 컨펌」 CTA
- 컨펌 후: 대회기록(`race_results`)에 반영, 홈/명단에 확정 표시
- 배번 없음: 컨펌 CTA 없음

### 5.2 API (신규 또는 최소 확장)

- 공개(또는 닉/배번 검증된) **self-confirm** 성격의 액션
- 입력: `eventId` + 본인 식별(출석 프로필 닉 + 저장된 배번 등, 기존 `update-bib` 신뢰 경계와 맞춤)
- 동작: 스크랩 대기 결과 중 **본인 배번** 행을 `race_results`에 `status: confirmed`로 저장
- 재컨펌: 기존 confirm 패턴과 같이 **해당 참가자 기록 덮어쓰기**(중복 방지)
- 총무 `bulk-confirm` / 이름 갭 `confirm-one`은 베타 주경로에서 사용하지 않음 (비상 수단으로 코드 잔존 가능)

> 신규 API가 필요하면 `_docs/justification/` 작성 + 사용자 승인 후 구현 (프로젝트 규칙).

### 5.3 매칭 키

- 스크랩·대기·컨펌의 주 키: **배번**
- 배번 없음 = 파이프라인 제외

---

## 6. BE 방침

- 거대 신규 운영 API를 만들지 않는다. **UI 통합** + **배번 스크랩 필터** + **참가자 컨펌**만 손댄다.
- `boarding-admin` / `ops` / `group-detail`의 **필요 기능**은 `event-admin`(및 회원 컨펌)에 모은다. 구 페이지 **폐기·리다이렉트는 선택**(베타 성공 조건 아님).
- 버스 Phase 1(`bus-boarding`)이 아직 main에 없으면 **머지 또는 동시 착수**가 선행 의존.

---

## 7. 철원 베타 성공 기준

| # | 기준 |
|---|------|
| 1 | 총무가 **링크 하나**(`event-admin`)로 준비→버스→배번 현황→스크랩까지 끝낸다 |
| 2 | 새벽에 탑승 **수동 ON** 후, 대리 체크로 미탑승을 처리할 수 있다 |
| 3 | **배번 있는 사람만** 스크랩되고, 배번 없음은 결과 대상에서 제외된다 |
| 4 | **참가자가 컨펌**해야 `race_results`(대회기록)에 올라간다 |
| 5 | 이름 동명이인/갭 고르기 없이 당일·당일 후 결과 작업이 끝난다 (오배번 등 예외만) |
| 6 | 회원 흐름: 버스 → 배번 → (스크랩 후) 내 기록 컨펌 → 명단·결과 |

## 9. 열린 결정 (계획 착수 시 짧게)

1. 참가자 컨펌 CTA를 **홈 / 명단·결과 / 둘 다** 중 어디에 둘지 (베타는 최소 하나).
2. self-confirm API를 `group-events` subAction으로 둘지, 별도 action으로 둘지 (정당화 문서에서 확정).
3. 스크랩 job 스키마에 배번 키·대기/컨펌 상태를 어떻게 표시할지 (기존 `scrape_jobs.results` 확장 vs 최소 필드).
4. 컨펌 전 **대기 기록 읽기** 경로: `detail` 확장 vs scrape-job 공개 조회 vs self-confirm preview — 회원 화면에 기록/순위가 보이려면 계획에서 클라이언트 계약을 고정.
