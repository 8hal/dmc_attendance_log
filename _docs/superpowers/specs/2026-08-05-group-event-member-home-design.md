## 1. 배경

버스 탑승·배번·결과 보드가 생기더라도, 회원 입장에서는 **단톡/카페에 뿌릴 한 링크**와 **모바일에서 바로 고를 수 있는 할 일**이 필요하다.  
기존 `group-detail.html`은 운영(갭·확정·스크랩) 중심이라 회원 입구로 쓰기 어렵다.

이 스펙은 **회원(참가자) 축만** 다룬다. 운영 셸·`group-detail` 전면 개편은 의도적으로 제외한다.

---

## 2. 목표 · 비목표

### 2.1 목표

- 대회별 **회원 홈** 한 페이지: 요약 + 큰 런처(버스 / 배번 / 결과)
- 같은 기기에서 출석부 프로필이 있으면 **닉네임 사전 선택** (선택 UI 최소화)
- 출석앱 **더보기** · 단톡/카페/QR에서 진입
- 당일 **일정 타임라인**은 접이식으로 두어 첫 화면을 늘리지 않음

### 2.2 비목표 (이번)

- 운영 모바일 셸, `group-detail` / `boarding-admin` 전면 UX 개편
- 서버 세션 토큰(춘백식 Bearer) 도입 — 출석 `localStorage` 프로필 재사용만
- 정모(`meeting_training` / `attendance`)와 스키마·컬렉션 통합
- 중식, 네이버 폼 API, 푸시/알림톡
- 타임라인 **편집 UI** (운영이 넣는 데이터만; 입력 화면은 후속)
- 공개 결과 보드 본구현 (런처는 “준비 중” 허용)

### 2.3 장기 비전 (한 절)

나중에 정모와 단체 대회를 묶는 공통 **Event** 추상화가 있으면 일정·딥링크·회원 홈 요약 관리가 쉬워질 수 있다.  
**이번 저장·조회·구현은 `race_events`만** 사용한다. 공통 Event 컬렉션/클래스는 도입하지 않는다.

## 3. 접근

**전용 페이지 `event-home.html?eventId=`** (Approach A).

| 대안 | 기각 이유 |
|------|-----------|
| `group-detail` 모드 분기 | 운영 FE와 섞여 회원 축만 미루는 목적과 충돌 |
| `boarding.html`만 입구 | 버스 off 대회·“하루 허브” 역할이 약함 |

하위 작업 화면은 기존 URL을 유지하고, 홈은 **런처·요약·일정**만 담당한다.

---

## 4. 정보 구조 · 진입

### 4.1 페이지 역할

| 페이지 | 역할 | 이번 변경 |
|--------|------|-----------|
| `event-home.html` | 회원 홈: 요약 · 런처 · 접이식 일정 | **신규** |
| `boarding.html` | 버스 셀프 탑승 | 사전 닉 규칙 정렬(필요 시) |
| `my-bib.html` | 배번 입력 | 사전 닉 규칙 정렬(필요 시) |
| 결과 보드 | 동행 기록 읽기 | 미구현 시 런처 비활성 |
| `attendance-v2` 더보기 | 「단체 대회」 진입 | 링크/소량 FE |
| `group-detail` / `boarding-admin` | 운영 | **손대지 않음** (허브 카드가 있어도 회원 입구로 쓰지 않음) |

### 4.2 진입 경로

1. **단톡/카페 고정 링크** → `event-home.html?eventId={id}`
2. **현장 QR** → 홈 또는 하위 딥링크 (`boarding.html?eventId=&leg=outbound` 등). 하위여도 §5 사전 닉 적용
3. **출석 더보기 → 「단체 대회」**
   - **후보 집합:** `isGroupEvent === true` 이고 `eventDate >= today(KST)` (당일 포함, **미래·당일만**. 과거 대회는 목록에 넣지 않음). 상한 일수 제한 없음(건수가 적다는 전제).
   - 후보 **1건** → 중간 목록 없이 바로 해당 `event-home`
   - 후보 **2건 이상** → 짧은 **회원용 목록 페이지**(신규 얇은 HTML 또는 `event-home` 쿼리 모드 중 구현 계획에서 택1; 이름·날짜·id만) → 탭 시 홈
   - 후보 **0건** → 목록 페이지를 열되 **빈 상태**: “예정된 단체 대회가 없어요” + 출석 앱으로 돌아가기. (과거 대회 브라우징 없음)
   - 운영 `group.html`은 더보기에서 연결하지 않음

## 5. 신원 · 사전 닉네임

서버 토큰 신설 없음. **같은 기기의 출석 프로필**을 재사용한다.

### 5.1 읽기 우선순위

1. `localStorage` `dmc_attendance_v2_profile` → `nickname` (및 있으면 `memberId`)
2. 없으면 `marathon_att_nickname`
3. 없으면 boarding / my-bib 전용 키

### 5.2 동작

- `event-home` · `boarding` · `my-bib`에서 로스터 또는 `participants`에 **동일 닉(또는 memberId) 매칭**이 되면  
  목록 선택을 건너뛰고 **“○○님으로 진행”** 확인(또는 동등한 사전 선택 상태)만 둔다.
- 없거나 불일치(다른 기기, 게스트, 명단 미매칭) → 기존 닉 선택 UI.
- 탑승/배번 성공 시 기존처럼 출석·boarding·bib 관련 localStorage 닉을 동기화한다.
- API는 지금과 같이 클라이언트가 보낸 `nickname` / `memberId`를 사용한다 (Bearer 없음).

### 5.3 게스트

버스 로스터 지인 등 출석 프로필이 없으면 **닉 선택 유지**.

## 6. 홈 화면 구성 (모바일 우선)

첫 뷰포트 = **대회 맥락 + 할 일 런처**. 통계·운영·전체 명단 없음.

### 6.1 상단 요약

- 제목: `eventName` || `primaryName`
- 한 줄: `eventDate` · `location`(있을 때만)
- 선택: 프로필 닉이 있으면 “○○님” 칩 (없으면 생략, 강요 없음)

### 6.2 런처 (세로 스택, 큰 터치)

| 런처 | 이동 | 상태 |
|------|------|------|
| 버스 탑승 | `boarding.html?eventId=` (+ optional `leg`) | `busBoarding.enabled`가 아니면 **숨김**. on이고 프로필 매칭 시 뱃지: **다음 미탑승 필수 구간**이 있으면 “미탑승”, 필수 구간이 모두 boarded면 “완료” (왕복이면 outbound→return 순으로 “다음” 판정) |
| 배번 입력 | `my-bib.html?eventId=` | 버스와 무관하게 노출. 내 배번 유무 뱃지(participants + 프로필 매칭 시) |
| 결과 보기 | 결과 보드 URL | 미구현이면 **비활성 + “준비 중”** |

홈에서 탑승 체크·배번 저장을 하지 않는다. **이동만**.

### 6.3 당일 일정 (접이식, Approach A)

- 위치: 런처 **아래**. 기본 **접힘** (`당일 일정 ▾`).
- 내용: 4–6줄 수준 `{ time, label }` (예: 집결 · 출발 · 레이스 · 복귀).
- 데이터 없으면 **섹션 자체 숨김**.
- 첫 화면을 늘리지 않는 것이 목적. 펼쳤을 때만 길이 증가.

### 6.4 하단

- 짧은 링크: 출석 앱(`attendance-v2.html`)으로 돌아가기 등.

## 7. 데이터 · API

### 7.1 저장소

- 대회 SSOT: `race_events` (`eventId` = 문서 id).
- 선택 필드 **`dayTimeline`**: `{ time: string, label: string }[]`  
  - 없거나 빈 배열 → 일정 섹션 숨김.  
  - 운영 입력 UI는 이번 비범위(시드·수동·추후 운영 도구).

집결 전용 `dayBrief` / 정모 `meeting_training`과 필드명 통일은 **하지 않는다** (장기 Event 추상화 때 재검토).

### 7.2 읽기

| 필요 | 수단 |
|------|------|
| 홈 요약 · participants · bus enabled | 기존 `group-events` `detail` (또는 동등 read) |
| 내 버스 상태 | 기존 `bus-boarding` `status` + 로컬 프로필 매칭 |
| 더보기 1건/목록 | 기존 group-events 목록 read 재사용, 또는 이름·날짜·id만 노출하는 **얇은 public list** |

신규 API가 필요하면 `_docs/justification/` + 사용자 승인 후 (프로젝트 new-api 규칙).  
큰 쓰기 API·운영 API는 회원 홈 범위에 넣지 않는다.  
기존 `group-events` 목록이 운영용 풀 페이로드면, 더보기/회원 목록은 **이름·날짜·id만** 쓰거나 얇은 public list를 검토한다(계획 단계).

### 7.3 모듈 독립 (기존 비전 유지)

- 버스 off여도 배번·결과 런처 정책은 §6.2.
- 배번·결과는 버스 탑승 여부에 종속되지 않음.

### 7.4 버스 Phase 1 의존

`boarding.html` · `action=bus-boarding` · `busBoarding` 필드는 **버스 Phase 1** 산출물이다. `main`에 없을 수 있다.

계획·구현 시:
1. **권장:** 버스 Phase 1이 머지된 베이스에서 `event-home`을 구현한다.
2. **병행 시 그레이스풀 디그레이드:** `bus-boarding`/`boarding.html`/detail의 `busBoarding`이 없으면 버스 런처를 숨기고, 배번·요약·일정·더보기 진입은 동작시킨다. 버스 API를 회원 홈 범위에서 재구현하지 않는다.

## 8. 상태 · 빈 화면 · 에러

| 상황 | UX |
|------|-----|
| `eventId` 없음 / 문서 없음 | “대회를 찾을 수 없어요” + 출석 앱 링크 |
| 단체 대회가 아님 | 동일(상세 이유 최소화) |
| 버스 off / 버스 Phase 1 미존재 | 버스 런처 숨김 (§7.4) |
| 더보기 후보 0건 | “예정된 단체 대회가 없어요” + 출석으로 |
| 결과 미구현 | 결과 런처 비활성 + “준비 중” |
| 프로필 ↔ 명단 불일치 | 홈은 표시. 하위 진입 시 닉 선택 폴백 |
| API 실패 | 인라인/토스트 “다시 시도”. 가능하면 런처 딥링크는 유지 |

## 9. 구현 Phase (스케치)

계획 문서에서 상세화한다. 스케치만:

1. `event-home.html` + detail/status 읽기 + 런처 + 접이식 `dayTimeline`
2. 사전 닉 규칙을 boarding / my-bib와 정렬
3. 출석 더보기 진입 + (필요 시) 회원용 짧은 목록
4. 결과 보드 연결은 보드 구현 시 런처 활성화

운영 셸·타임라인 편집·Event 추상화는 별도 트랙.

---

## 10. 성공 기준

- 단톡 링크 하나로 모바일에서 대회 맥락과 버스/배번(·결과) 진입이 된다.
- 출석 프로필이 있는 기기에서는 하위 화면에서 닉 선택을 대부분 건너뛴다.
- 일정은 기본 접혀 있어 첫 화면이 런처 중심이다.
- 운영 페이지를 열지 않고도 회원 플로우가 완결된다(결과 보드 전까지는 “준비 중” 허용).
