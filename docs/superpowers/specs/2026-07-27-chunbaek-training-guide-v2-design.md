## 1. 목표

**성공 기준**
1. `/chunbaek/guide/` 한 URL에서 DOCX 본문(사용법~부록·참고)을 스크롤·목차로 읽는다.
2. 핵심 판단은 **표**와 **인라인 SVG(기본 4종)** 로 스캔 가능하다.
3. 일지 사례는 카톡 원문이 보이며, 해석은 원문 아래 1~2문장으로만 덧붙인다.
4. 완주형·향상형·기록형·상급형 **열/처방표는 웹에 다시 넣지 않는다.**

**실패·롤백**
- 4수준 거리·페이스 처방표가 부활
- 카톡 사례를 윤문으로 대체
- 모바일에서 표가 가로로만 깨져 내용을 읽지 못함

## 2. 합의된 전제

| 항목 | 결정 |
|------|------|
| 생동감 | 하이브리드 — DOCX 문체·논리 + 장마다 표 1~2 + 그림(기본 SVG / 추가 이미지는 슬롯) |
| 페이지 | **단일 롱스크롤** + 목차 앵커 |
| 범위 | DOCX **거의 전부** (1~16장 + 부록 + 참고) |
| 4수준 표 | **전원 공통 표**로 재작성. 차이 = 세 구간 메모 + 그림 |
| 독자 구간 | 서브3 / 싱글 / 330+첫풀 (앱 `goalMarathonNetTime` 분포 참고) |
| 현실 모델 | 요일 훈련 고정, 팀은 페이스·해석 |
| 추가 그림 | 사용자가 검색·삽입 가능 (`figures/` 슬롯) |
| 구현 형태 | HTML 한 장 + CSS + 인라인 SVG (md 빌드 없음) |
| 브랜치 | 기존 feature 브랜치에서 v1 가이드 파일 교체 |

시각 디자인 전용 스킬은 레포에 없음. 매뉴얼 디자인 관행(표·콜아웃·다이어그램으로 스캔)을 따름.

## 3. 정보 구조 (IA)

```
/chunbaek/guide/index.html
  #intro-usage      사용법 · 기본 원칙
  #intro-diary      일지 사례를 읽는 방법 (원문 붙여넣기 규칙)

## 5. 표 변환 규칙

1. DOCX `add_table` 내용을 기본 이관한다.
2. **수준 4열(완주형…상급형)이 있는 표**는 웹에서:
   - 열을 제거하거나,
   - 「공통 목적 / 공통 범위」 한 줄로 합치고,
   - 구간 차이는 `.band-notes` + (필요 시) 다이어그램으로만 설명한다.
3. 페이스·km **처방**이 목적인 칸은 “범위·감각·RPE” 서술로 완화한다. DOCX가 이미 RPE 우선을 말한 곳은 그 문장을 살린다.
4. 숫자 표(페이스 환산, A/B/C 등) 중 **전원 공통으로 의미 있는 것**은 유지한다.

## 6. 다이어그램 (기본 4 + 슬롯)

**구현이 넣는 인라인 SVG (필수 id)**
1. `#diagram-100day-timeline` — 100일 5단계 타임라인 (DOCX 4장 근처)
2. `#diagram-week-framework` — 주간 틀 화·목·토 공통 목적 (DOCX 5장 근처)
3. `#diagram-decision-flow` — 통증·실패 의사결정 (부록 B 요약). **DOM 위치: `#ch-9` 끝.** `#ch-10`에서는 같은 그림으로 앵커 링크만 (`#diagram-decision-flow`)
4. `#diagram-race-abc` — 레이스 A·B·C (DOCX 15장 근처)

**사용자가 넣을 수 있는 슬롯 예**
- 장거리/보급/코스 사진, 외부 인포그래픽  
- 파일: `chunbaek/guide/figures/`  
- 마크업: `<figure class="figure-slot" data-figure="optional-name"><div class="figure-slot__placeholder">이미지 자리 — figures/에 파일을 넣으세요</div><figcaption>...</figcaption></figure>`  
  (이미지 추가 시 placeholder를 `<img>`로 교체)

## 7. 카톡 원문 규칙

1. `source/KakaoTalk_Chat_*.txt`에서 **해당 장면을 잘라 그대로** 넣는다.
2. 맞춤법·톤 윤문 금지. 날짜 헤더·ㅡ 줄·이모티콘성 ㅋㅋ/ㅠㅠ 유지.
3. 앞에 라벨: `일지 원문`.
4. 아래에만 DOCX 「사례 해석 규칙」에 맞는 `.guide-note` (권장 아님 / 판단 연습).
5. 한 장에 원문이 과도하면 `<details open>` 또는 접기 기본은 열린 상태·접기는 선택.

## 9. 기술 구성

```
chunbaek/guide/
  index.html

  guide-nav.js      # 섹션 목록 SSOT, 목차/이전·다음 앵커

- Functions/Firestore/SW 변경 없음 (SW에 guide 캐시 추가는 비범위).

- 테스트 스모크:
  - `index.html` + `#intro-usage` … `#ch-16` · `#app-a` … · `#refs` 앵커 존재
  - 필수 SVG id 4개 존재
  - `.guide-story--raw` 최소 1개 + 카톡 원문 마커(예: `ㅡ`)
  - **금지:** 표 헤더에 `완주형`/`향상형`/`기록형`/`상급형`이 **연속 열으로** 등장하는 패턴

  - 나 탭 → `/chunbaek/guide/` (온보딩 `#/guide` 아님)
